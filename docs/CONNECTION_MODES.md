# Connection modes

Choose **Bot only** or **With game client** under Account & character. A saved local login retains the choice; older profiles without a mode keep the official game client. Only one connection is owned at a time. Disconnect explicitly before changing mode or account. Opening panels or navigating the companion never changes connection mode.

Bot only loads a bundled controller webview, with no official HTML navigation, Unity execution, renderer or game UI. Rust owns authentication and character selection at the fixed TLS endpoint `wss://gamesea01.rayrag.com/ws`. Credentials, authentication packets, character-approval bodies and optional tokens remain native. The local runtime receives ordinary gameplay frames, a connection event and ordered observations of successful Enter/Ready writes. Both modes use the same controller and outgoing gameplay codecs. Map metadata still comes from fixed public assets; failures use observed monsters. Collision/pathfinding data remain bundled.

Before authenticating, native requests only the public version file and bounded official HTML as inert compatibility text, with normal certificate checking, no redirects and the identifying `Rayrag-Companion` user agent. The verified contract is version 8 and `Build_2569-09-01-01-55`, from public source revision `4099e2c000c3c550516760b9c1241595aac9aceb`. No Unity assets execute in Bot only.

Initial Ready requires processed Enter, the first complete inventory/skills/stats packet and complete memo data. A processed map change sends one Ready. Native flush observations stay ordered with incoming frames. Resource uncertainty is released only by the existing controller certificate, including a matching first own entry and unchanged resource revisions. Application Ping runs natively every five seconds, including character selection and in-world Stop. Stop ends automation while leaving in-world receipts observable; pre-world Stop cancels the transport. Disconnect, runtime destruction and main-window closure invalidate native ownership and abort the socket. A replacement waits for retired transport completion.

Native queues and frames are bounded. Socket reads pause before the queue reaches its event or byte limit; outgoing writes, Ping and cancellation remain available. Capacity reserves cover one Ready acknowledgement per event in a polled batch and a terminal event. Frame deliveries remain owned until the runtime acknowledges processing them. Maintenance freezes new sends, including Ping; queued frames, outstanding writes, delivery processing and cancellation prevent stale update acknowledgement. Incoming frames continue to be applied during a held lease. Async write rejection does not confirm a game action and retains unresolved outcomes conservatively.

Warp uncertainty also has a native, user-only local originating-mode marker shared across webview origins. Disconnect, app restart and an opposite-mode clean snapshot cannot clear it. Reconnect the originating mode and complete authoritative initialization before switching. Native issues a one-use initialization permit for that new runtime; a later Warp mark cannot refresh that permit, and older asynchronous clears cannot remove a newer hold. Recognized official Warp packets wait for persistence before forwarding once on their captured socket. Other official game sends preserve their existing synchronous handling.

Feature-local tests use synthetic profiles and a local WebSocket server, never an actual account. They cover authentication bytes, existing-slot selection, actual native writes, Ping/Stop, denial, write failure, cancellation, retirement generations, ordered initialization, stale resources, mode migration, native mode holds and updater races. Burst tests cover event and byte limits, ordered drain, successive batches of small and large frames, and outgoing writes while reads pause. The anonymous native compatibility probe verifies the two public GETs separately.

Real native gameplay was checked on 2026-10-03 in both modes using the local v0.2.48 QA package. Bot only entered `prt_fild08` without the official renderer and recorded 8 server-attributed defeats and 14 confirmed pickups in 83 seconds. With game client recorded 4 defeats and 6 confirmed pickups in 91 seconds. Both runs retained the two-death cap and stopped through the companion. These bounded runs establish login, occupied-character selection, map initialization, movement, basic combat and pickup acceptance. They do not establish long-duration background behavior, other maps, network-loss recovery or advanced resource actions. See [local verification](LOCAL_FEATURE_VERIFICATION.md) for the detailed proof limits.
