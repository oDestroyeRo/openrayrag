# Bounded supply trips

Supply trips are disabled by default. In **Travel & follow**, enable stock and/or weight triggers, choose verified storage/buy/sell services, and set finite trip, command, duration, interval and reserved-spending limits. Protected per-item disposition rules remain in **Inventory & skills**. **Preview supply trip** is pure: it explains current goals and the next service without moving, opening an NPC or spending resources.

A stock trigger fires below a configured minimum and captures the desired amount before leaving. Partial refill that crosses the minimum continues toward that captured desired amount. A weight trigger fires at its start percentage and requires observed weight strictly below the end percentage. Unknown inventory, current weight, capacity, equipment or ammunition prevents departure. A stable trigger stays latched until its captured recovery is observed. Recovery rearms the trigger immediately; the separate minimum interval still prevents an early departure. The trip allowance is consumed at attempted departure, including failed visits.

The controller retains the field settings, counters, character and actual map/cell. It settles movement, casts, resource actions and equipment before handing movement to the existing service/travel owner. Every NPC action uses fresh identity, complete menu contracts and source-backed service definitions. Stock is replanned after each exact receipt. Excess disposition precedes refill, with store → cart → sell priority; unknown preferred storage cannot authorize a fallback sale. Observed full storage permits a later destination only after confirmed NPC closure; the trip retains only that capacity fact across its own travel, and discards it on interruption or unexpected context change. Equipped and selected ammo, refined/carded/unknown unique items, recovery reserves, selected escape-wing reserves and compatible loadout ammunition reserves remain protected by the shared disposition rules.

Only one revalidated economic action is sent at a time. The exact stock/currency expectations and transfer source/destination evidence are captured before dispatch, including a transport exception. NPC end, map changes, Stop, manual input, death, timeout or a closed shop do not establish transaction success or authorize replay. A late exact receipt may drain ownership without resuming a canceled trip. Context reset requires both fresh inventory and currency to release uncertainty; the old outcome is labeled unknown and the interrupted trip remains disarmed. A transaction is never inferred as failed merely because time passed.

One finite cap covers the whole trip. Actual confirmed expenditure and conservative reservations are tracked separately; sales do not replenish the spending cap. Discounts follow the pinned server's item-ID debit formula, while reservations use the higher of the server and displayed quotes. Budget/stock/capacity limits can yield a safe partial batch; no stock, price, service fee or capacity is invented. Every Tool Dealer purchase/sale closes the interaction, so the next batch reopens and resolves a fresh verified service. Storage is also closed and confirmed between batches.

After the captured goals are met and NPC closure is observed, portal travel returns to the captured map and a final verified approach returns to the exact captured work cell. Only then may the retained field run resume. Failed return, unexpected map, manual yield or death leaves an explicit waiting reason. Emergency escape can preempt service travel/approach after movement settlement; it cannot overlap unresolved economics, casts or gear. HP recovery interrupts the trip without resuming combat at the service location.

The main-window field-run memory retains a bounded, config-free guard through reconnect/page reload and Stop: remaining trips, latch, interval, conservative expenditure/uncertainty and return destination. Actor IDs, transaction commands, menus, receipts and credentials never persist. A never-enabled supply runtime allocates no guard or allowance. The first explicit enabled Start reserves its configured allowance in main-window memory before awaiting the game page, so an immediate page reload cannot replenish an unreported departure. A blank new page or a disabled supply setting cannot replenish a previously enabled allowance. Validated Start/resume transfers the retained guard to the successor page, allowing its fresh reconciliation to clear uncertainty without restoring spent trips. A delayed completion cannot overwrite newer sent/reconciled telemetry, and the guard registry remains capped at 64 characters. A reload conservatively disarms an interrupted trip until fresh economics reconcile, followed by explicit user intervention; an unknown prior return destination also holds field continuation; it never retransmits an earlier economic request. An explicit new field run can retain the remaining allowance after reconciliation without resuming the canceled trip.

## Guard transitions

| Transition | Required retained state |
| --- | --- |
| Never enabled → first enabled | No dormant guard; allocate the configured allowance once. |
| Enabled/spent → disabled → enabled | Preserve consumed trips, interval, latch and reservations. |
| Stop → explicit Start | Cancel continuation; clamp allowance locally and in the main window. |
| Old page → validated successor | Transfer ownership; fresh readback may reconcile uncertainty without claiming the old outcome. |
| Delayed Start completion → newer publication | Preserve the current owner's uncertainty, latch, destination and timers; never restore allowance. |
| Foreign/malformed guard → rejected Start/configuration | No run intent, runtime reset, allowance change or commands. |
| Superseded Start/resume completion | Generation/owner checks reject the obsolete handoff. |
| 64 retained characters → another character | Keep the registry bounded; unknown overflow remains disarmed. |

These transitions are covered by the synthetic controller/runtime/resume tests. Only an exact receipt or fresh inventory-and-currency reconciliation can release resource uncertainty; neither path retries the old command.

## Evidence and limits

Implementation and tests use Rebuild commit `4099e2c000c3c550516760b9c1241595aac9aceb`, the owning [disposition contracts](item-disposition.md) and [NPC service contracts](NPC_SERVICES.md). The Field05 Tool Dealer is registered at `(290,221)` in `PronteraShop.txt:52–61`; `NpcTraderBase.cs:7–26` supplies the exact Buy/Sell/Cancel menu and closes each batch. Shop debit/proceeds are from `Npc.cs:710–807`; normal storage/cart/inventory handler capacities and delta layouts are documented in `PROTOCOL.md` and the disposition source notes. The portable service presets declare zero opening fees at this pin; edited or unknown contracts remain blocked.

Synthetic tests cover complete same-map and cross-map service/return ownership, exact return cell, partial refill crossing minimum, budget/stock/capacity guards, protected floors, changed menus/prices, Stop stages, timeout/manual/death/transport exception, late exact receipts, reconnect readback, finite allowance/latch and profile/native schema parity. A cross-map controller test uses a captured cell distinct from the portal arrival and verifies that field resumption waits for the final approach. Renderer regressions cover completion/cancellation replacing active status and preserve a later pure preview while telemetry is unchanged.

A controlled native macOS test on 2026-10-02 deposited one existing stackable item, then ran one storage-only supply trip with combat and loot off, a zero spending cap, 30 commands and a 300-second deadline. The client traveled from `prt_fild08` to the verified Prontera storage service, withdrew exactly one item, confirmed storage closure and returned to the captured `prt_fild08` cell `(170,375)`. Inventory was restored, currency was unchanged and no trips remained. Stop returned the client to Ready and app exit was verified. The captured cell coincided with portal arrival; a nontrivial final approach is covered by synthetic tests rather than this native run. The run exposed stale terminal status text, corrected with renderer tests before delivery. The native app was built and its ad-hoc signature verified; it is not notarized.

This test does not establish live buying/selling, cart fallback, full-capacity behavior, interrupted transaction recovery, reconnect or broader unattended supply behavior. Those remain synthetic/source-backed proof and explicit live-validation gaps.
