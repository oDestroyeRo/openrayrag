# Bounded supply trips

Supply trips are disabled by default. In **Setup → Loot & supplies → Auto sell**, enable trips, set weight thresholds, choose sale items and retained quantities, select a merchant and transport, and set finite trip, command, duration, interval and reserved-spending limits. Ordinary setup uses the verified merchant choices; editing service JSON is optional. Stock triggers, storage/buy services and additional limits are under **Optional refill, storage and trip budgets** in the same section. With no storage/buy service configured, enabling trips selects the weight trigger and automatic merchant selection when no explicit merchant is selected.

The protected item table uses **Maximum** as the quantity retained before excess becomes eligible, **Keep** as a floor, and an explicit **Sell** permission. Unlisted items remain protected. **Preview auto sell & supply trip** sends no commands: it lists eligible quantities, protected items, the captured return cell, available merchant/approach, limits and an unmet weight goal. Prices and exact sale proceeds require a fresh shop; preview does not authorize a transaction. Form/Script and profiles retain the same settings. Saving or previewing never starts a trip, and edits retain the existing Apply/Next run behavior.

A stock trigger fires below a configured minimum and captures the desired amount before leaving. Partial refill that crosses the minimum continues toward that captured desired amount. A weight trigger fires at its start percentage and requires observed weight strictly below the end percentage. Unknown inventory, current weight, capacity, equipment or ammunition prevents departure. A stable trigger stays latched until its captured recovery is observed. Recovery rearms the trigger immediately; the separate minimum interval still prevents an early departure. The trip allowance is consumed at attempted departure, including failed visits.

For example, start at **80%** and finish **below 60%**. Set the start threshold below an enabled hard weight stop: reaching that stop before the first trip command, including during preparation, prevents departure. If permitted sales cannot meet the lower threshold, the trip waits with a reason; it does not sell protected stock or repeat trips to force the target.

When the last permitted sale leaves weight above or equal to the finish threshold, the waiting reason shows the observed percentage, weight/capacity and required strict threshold. For example, **25740/34900 = 73.75%** cannot finish a trip configured for **below 70%**, even after every permitted drop was sold. Protected stock stays retained. Review the finish threshold against the stock you intend to keep, configure permitted storage, or explicitly review item permissions. Then use the interrupted-trip Stop/Start recovery below; changing a threshold never completes or retries the trip by itself.

**Automatic merchant** considers source-backed ordinary NPC sell contracts reachable under the current map policy, prefers the actual arrival map, and ranks permitted portal-route and collision-aware walking costs. If no portal route exists, a supported, permitted Database destination may be selected without inventing a landing cell or route cost; preview identifies that uncertainty. **Choose map / NPC** retains an explicit verified merchant. A sprite, nearby actor or player vending shop cannot establish sale capability. When service travel uses Database teleport, the destination map stays owned by the same trip and the automatic choice is reranked from the actual landing cell before NPC approach. No reachable merchant on that arrival map leaves an explicit wait. Every visit still requires fresh exact identity and the complete expected menu.

**Trip transport** offers normal service travel, **Butterfly Wing #602**, or the separate learned **Return skill #54**, level 1, costing 10 SP at the protocol pin. Item/skill return requires a configured **expected save-point map code**, permitted map/collision data and fresh stock or learned-skill/SP evidence. Butterfly stock must cover the one consumed wing plus the configured retained reserve; that reserve remains protected even when emergency escape is off. The existing return adapter supplies its settlement wait, shared cooldown, one-shot receipt and bounded arrival deadline. Inventory removal or SP debit alone cannot confirm return: the same living character must refresh and arrive on the configured map. Merchant selection uses that actual cell, never an assumed save cell. A wrong map, rejection, unavailable stock/SP, cooldown or unconfirmed arrival holds the trip.

**Unstuck / return command** is visibly unavailable because the deployed alive-return contract is unverified. At the pin, [client `/return`](https://github.com/Doddler/RagnarokRebuildTcp/blob/4099e2c000c3c550516760b9c1241595aac9aceb/RebuildClient/Assets/Scripts/PlayerControl/ClientCommandHandler.cs#L188-L191) sends Respawn and [the server rejects living characters](https://github.com/Doddler/RagnarokRebuildTcp/blob/4099e2c000c3c550516760b9c1241595aac9aceb/RoRebuildServer/RoRebuildServer/Networking/PacketHandlers/Character/PacketRespawn.cs#L29-L30). Selling trips never induce death or substitute death respawn for alive return. See the [ordinary return contracts](PROTOCOL.md#ordinary-emergency-escape).

The controller retains the field settings, counters, character and actual map/cell. It settles movement, casts, resource actions and equipment before handing movement to the existing service/travel owner. A supply-owned save return uses that same trip allowance and excludes competing field/escape/economic dispatch; it does not create an emergency danger episode or resume farming before the sale. Every NPC action uses fresh identity, complete menu contracts and source-backed service definitions. Stock is replanned after each exact receipt. Excess disposition precedes refill, with store → cart → sell priority; unknown preferred storage cannot authorize a fallback sale. Observed full storage permits a later destination only after confirmed NPC closure; the trip retains only that capacity fact across its own travel, and discards it on interruption or unexpected context change. Equipped and selected ammo, refined/carded/unknown unique items, recovery reserves, selected escape-wing and supply-return reserves, and compatible loadout ammunition reserves remain protected by the shared disposition rules.

Only one revalidated economic action is sent at a time. The exact stock/currency expectations and transfer source/destination evidence are captured before dispatch, including a transport exception. NPC end, map changes, Stop, manual input, death, timeout or a closed shop do not establish transaction success or authorize replay. A late exact receipt may drain ownership without resuming a canceled trip. Context reset requires both fresh inventory and currency to release uncertainty; the old outcome is labeled unknown and the interrupted trip remains disarmed. A transaction is never inferred as failed merely because time passed.

An interruption or terminal planning blocker retains its original reason after the whole-trip deadline; the elapsed timer does not replace an unmet weight goal, service failure or exact-receipt timeout with a generic limit warning. A duration limit reached during an active stage distinguishes a pending exact transaction receipt from a trip with no pending transaction. Waiting blocks further supply commands without consuming command allowance. Late exact receipts can still reconcile an interrupted transaction, but do not resume the trip.

One finite command and spending cap covers the whole trip, including explicitly authorized replacements after interruption. **Commands per trip** accepts 1–1000 and defaults to 100. Movement segments, Database travel and NPC interaction all count, so longer merchant routes may need a higher limit. Stop/Start preserves commands already used. Actual confirmed expenditure and conservative reservations are tracked separately; sales do not replenish the spending cap. Discounts follow the pinned server's item-ID debit formula, while reservations use the higher of the server and displayed quotes. Budget/stock/capacity limits can yield a safe partial batch; no stock, price, service fee or capacity is invented. Every ordinary trader purchase/sale closes the interaction, so the next batch reopens and resolves a fresh verified service. Storage is also closed and confirmed between batches.

After the captured goals are met and NPC closure is observed, existing travel returns to the captured map and a final verified approach returns to the exact captured work cell. Only then may the retained field run resume with its original counters and run/death/session limits. Failed return, unexpected map, manual yield or death leaves an explicit waiting reason. Emergency escape can preempt service travel/approach after movement settlement; it cannot overlap an owned save return, unresolved economics, casts or gear. HP recovery interrupts the trip without resuming combat at the service location.

The final return may follow a verified route across the full finite collision grid, because a Database landing can be far from the captured work cell. NPC and other final approaches retain their 512-cell cap. Return uses the same travel owner, five-minute approach deadline, movement receipts, step size and cumulative supply-command allowance; a nudge or replan does not renew them. Reaching the correct map alone still cannot resume the field run.

The main-window field-run memory retains a bounded, config-free guard through reconnect/page reload and Stop: remaining trips, latch, interval, conservative expenditure/uncertainty and return destination. Actor IDs, transaction commands, menus, receipts and credentials never persist. A never-enabled supply runtime allocates no guard or allowance. The first explicit enabled Start reserves its configured allowance in main-window memory before awaiting the game page, so an immediate page reload cannot replenish an unreported departure. A blank new page or a disabled supply setting cannot replenish a previously enabled allowance. Validated Start/resume transfers the retained guard to the successor page, allowing its fresh reconciliation to clear uncertainty without restoring spent trips. A delayed completion cannot overwrite newer sent/reconciled telemetry, and the guard registry remains capped at 64 characters. Reloads and automatic update continuation keep a latched trip with a captured destination disarmed, including settled same-page handoffs. Fresh economics alone never grant retry permission; an unknown prior return destination also holds field continuation. Neither reload nor Stop/Start replays a sent save return or sale.

To recover an interrupted latched trip, **Stop**, check its outcome, correct the merchant if needed, choose **Travel to selected merchant**, then explicitly **Start**. If the actual Database arrival has no verified escape, use normal manual Database travel to a verified walkable cell first; automation does not force blocked terrain or repeat the teleport. Start holds field automation, including configured-field entry, until fresh living observations of the same character, known economics, settled actions, the retained minimum interval and current map policy permit a new attempt. It consumes another remaining trip exactly once and starts that attempt's duration deadline; cumulative commands, expenditure, conservative reservations and the original work map/cell remain unchanged. Changing settings, restoring a page or reconciling a late receipt cannot grant this permission. Stop, death or connection change cancels it. Interrupted Butterfly/Return-skill trips require switching to normal travel; no save-return departure is replayed. If fresh observations already satisfy the captured goals, the replacement closes and returns without another transaction. Exact economic receipt, NPC closure and return to the original cell still precede field resume.

Recovery also requires the current farming destination to match the captured work map, using the existing lock-area → explicit travel destination → configured map precedence. Restore an incompatible farming destination before Stop/Start; editing it cannot move the interrupted trip's captured work cell.

## Guard transitions

| Transition | Required retained state |
| --- | --- |
| Never enabled → first enabled | No dormant guard; allocate the configured allowance once. |
| Enabled/spent → disabled → enabled | Preserve consumed trips, interval, latch and reservations. |
| Stop → explicit Start | Keep the latch, original work cell and cumulative caps; request one new attempt charged to remaining trips after fresh settlement and the retained interval. |
| Automatic reload/update → Start | Keep a latched captured trip disarmed, even for a settled same-owner handoff. |
| Old page → validated successor | Transfer ownership; fresh readback may reconcile uncertainty without claiming the old outcome. |
| Delayed Start completion → newer publication | Preserve the current owner's uncertainty, latch, destination and timers; never restore allowance. |
| Foreign/malformed guard → rejected Start/configuration | No run intent, runtime reset, allowance change or commands. |
| Superseded Start/resume completion | Generation/owner checks reject the obsolete handoff. |
| 64 retained characters → another character | Keep the registry bounded; unknown overflow remains disarmed. |

These transitions are covered by the synthetic controller/runtime/resume tests. Only an exact receipt or fresh inventory-and-currency reconciliation can release resource uncertainty; neither path retries the old command.

## Evidence and limits

Implementation and tests use Rebuild commit `4099e2c000c3c550516760b9c1241595aac9aceb`, the owning [disposition contracts](item-disposition.md) and [NPC service contracts](NPC_SERVICES.md). The Field05 Tool Dealer is registered at `(290,221)` in `PronteraShop.txt:48–57`; the catalogue also includes twelve pinned town sell contracts. `NpcTraderBase.cs:8–27` supplies the exact Buy/Sell/Cancel menu and closes each batch. Shop debit/proceeds are from `Npc.cs:710–807`; normal storage/cart/inventory handler capacities and delta layouts are documented in `PROTOCOL.md` and the disposition source notes. The portable service presets declare zero opening fees at this pin; edited or unknown contracts remain blocked.

Synthetic tests cover complete same-map and cross-map service/return ownership, exact return cell, partial refill crossing minimum, budget/stock/capacity guards, protected floors, changed menus/prices, Stop stages, timeout/manual/death/transport exception, late exact receipts, reconnect readback, finite allowance/latch and profile/native schema parity. A real resolver/controller regression reproduces the unusable actual Izlude arrival at `(145,181)`, then explicitly recovers after manual relocation and merchant correction, confirms an exact sale and returns to a captured cell distinct from the return arrival before field resumption. It also holds through the retained interval after the old deadline expires. Runtime and retained-guard tests cover automatic handoff disarming and rejected stale, dead, foreign, uncertain, exhausted or restricted recovery. Renderer regressions cover completion/cancellation replacing active status and preserve a later pure preview while telemetry is unchanged.

A controlled native macOS test on 2026-10-02 deposited one existing stackable item, then ran one storage-only supply trip with combat and loot off, a zero spending cap, 30 commands and a 300-second deadline. The client traveled from `prt_fild08` to the verified Prontera storage service, withdrew exactly one item, confirmed storage closure and returned to the captured `prt_fild08` cell `(170,375)`. Inventory was restored, currency was unchanged and no trips remained. Stop returned the client to Ready and app exit was verified. The captured cell coincided with portal arrival; a nontrivial final approach is covered by synthetic tests rather than this native run. The run exposed stale terminal status text, corrected with renderer tests before delivery. The native app was built and its ad-hoc signature verified; it is not notarized.

This test does not establish live buying/selling, automatic merchant selection, Butterfly/Return-skill selling trips, cart fallback, full-capacity behavior, interrupted transaction recovery, reconnect or broader unattended supply behavior. The expanded merchants have pinned script/menu and bundled collision evidence; their deployed menus and complete auto-sell-and-return behavior remain explicit live-validation gaps.
