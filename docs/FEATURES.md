# Companion feature inventory

Companion implements its own typed engine, protocol adapter and interface. This inventory records supported behavior, unavailable systems and remaining implementation gaps.

This inventory covers **36 feature areas** across field automation, manual controls, profiles, condition routines, conditional macros and potential extensions. An area can contain both implemented and missing behavior; **Implemented subset** identifies the supported portion and its limits.

**Status is implementation coverage, not full deployed-game proof.** Historical expanded-release evidence includes 708 TypeScript tests, 25 Rust tests, build/typechecks, Clippy, independent review, native packaging and signature verification. Native validation covers session-only login, character selection, combat, pickup, inventory/skill/SP telemetry, Stop, death waiting, manual respawn across maps and sitting recovery. Reconnect and resource-changing workflows retain synthetic/source evidence; source protocol support alone does not establish live server behavior. See the README for exact proof limits.

**Partial** means a supported portion exists and the row lists what remains. **Not implemented** means no corresponding client behavior is provided. **Unverified** means matching deployed-game contracts have not been established; absence from the pinned public protocol is not proof the live game lacks the system.

The Rayrag action contracts use Rebuild pin **`4099e2c000c3c550516760b9c1241595aac9aceb`**; see [protocol evidence](PROTOCOL.md).

## Remaining implementation boundaries

Known ordinary-player contracts still needing client implementation include automatic warp casting, catalyst/automated refining and broader crafting. Manual chat/emotes, current-location memo slots, one-card socketing and one-attempt refining have separate explicit adapters; these do not enable automatic social messages, memo updates or socketing/refining. Combat needs verified policies beyond the three bolt skills and manual Thunderstorm, skill-specific ammunition, kiting, combos and broader party support beyond stationary Heal. Protected item plans and opt-in finite supply trips are implemented with the limited evidence described above; richer NPC input and broader service catalogs remain gaps. Profiles, routines and macro scripts use Companion's bounded data schemas; they cannot execute code. Macro/controller/UI verification is local, and live macro behavior remains unverified.

Direct player trading, guild/friend/clan, pets and other companions, quest logs/claims, mail/bank/auction/cash-shop systems need a matching verified Rayrag contract before adapters can be added. A similarly named source opcode or a configurable UI field is insufficient evidence.

## Preserved invariants

- One owner dispatches an action at a time. Server replies and authoritative state remain distinct from commands sent.
- Fixed origin, socket and build gating precede gameplay commands; malformed supported data blocks action until validated state exists.
- Client Stop and window close cancel run intent. Temporary interruption may retain intent while invalidating pending work; it must not repeat an uncertain resource transaction.
- Movement keeps one outstanding leg because the protocol has no request IDs. Walking permission is not evidence of projectile line of sight.
- Credentials are owned by native login state/optional local saved profile, never settings profiles, exports or telemetry. Tests use only synthetic accounts.
- New features remain opt-in and preserve current user choices.

## Verification before release

Run `npm run check`, formatting verification and `npm run app:build`; inspect the integrated diff and app signature. Protocol additions require fixed fixtures and malformed-bound tests. Resource actions require state readback, cancellation/late-response tests and no duplicate request after uncertainty. Persistent running requires tests for map changes, temporary loss, continued decisions during manual input, exhausted limits and Stop cancelling every retry. Native tests must report exactly which action families were exercised; unvisited maps and untested transactions remain explicit gaps.

Bounded command-only Walk and explicit visible-monster normal Attack now use the same physical navigation, field policy, range/LOS and observed arrow reserve as field combat. They retain cancellation receipts and never create field/reconnect intent, acquire replacements, loot, or execute strategies. See [manual target behavior and proof limits](MANUAL_TARGETS.md).

Actor ID zero is supported through the bounded entity, observation, combat, NPC and explicit action paths. Own readiness requires Enter plus an observed kind-0 entity; zero never stands in for unknown self. Selected-target and offline-party zero sentinels retain their source limitations. See [actor identity contracts and evidence](ACTOR_IDS.md).
