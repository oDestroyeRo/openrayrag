# Automatic respawn, recovery and return

The Recovery panel groups the existing opt-in save-point respawn, death allowance and return-to-farming-map settings. Defaults remain disabled. A requested run captures its farming map at explicit Start: the lock map, otherwise the configured journey destination, otherwise the requested field map. Selected monsters, loot policy and session counters stay attached to that run.

The controller suspends field decisions after death, settles previous owners, and waits a two-second quiet interval after its sends or actual official-client gameplay commands before the single respawn attempt. Opening inventory or another local panel only yields decisions. The quiet interval is a client precaution; it cannot establish the server's input budget. Respawn has no request ID or unique ACK, and an unanswered or throwing send never authorizes a second attempt for that death.

A living own-character refresh admits recovery: same-map clear followed by Warp entry 2, cross-map map change followed by EnterServer entry 1, fresh own Enter initialization after reconnect, or an authoritative own Resurrection. Map alone, a heal, another actor, ordinary entry 0, or the wrong entry subtype does not prove readiness. Observing revival reconciles current living state without attributing it uniquely to the old request. Nearby own broadcasts carry placeholder SP 0/0; known SP survives same-connection field resets, while a new connection needs its own authoritative SP state.

When sitting recovery is enabled, the existing scheduler confirms Sit, reaches the configured HP/SP end thresholds, and confirms Stand before travel. A Novice still needs verified Basic Mastery 2, and enabled SP recovery needs known SP. No recovery spending or fallback action is added. Recovery failures and unconfirmed posture writes remain waiting, without repeating a posture request. Return uses the existing collision, portal, lock and allow/deny policies; failed travel does not get a fresh deadline. Field activity resumes only at a ready, living, standing character with observed HP in the permitted farming destination/area.

The runtime-only death guard contains character, captured destination, phase, uncertainty and bounded absolute recovery/return deadlines. It contains no actor IDs, command payloads, inventory or credentials, and is excluded from profiles. The native and TypeScript boundaries share a strict corpus. The main window keeps at most 64 character guards. Replaced pages conservatively hold a still-dead episode even when dispatch telemetry was missed; a fresh living own initialization reconciles it. The original capability to finish recovery/return survives a final counted death even when future respawns are disabled. Prospective-page telemetry outranks an older Start completion. Restore clamps future timestamps to the finite policy duration and preserves any earlier deadline.

Stop cancels continuation at every phase. Late arrival or posture evidence can drain the held request, but cannot resume a stopped run. An explicit new Start discards a reconciled old continuation; outstanding respawn or posture uncertainty remains held. Daily hours, original wall/death/session allowances, other resource owners, and manual command settlement still apply.

An unconfirmed old recovery posture can also reconcile against the matching living character's known posture in a genuinely newer connection's own Enter initialization. This establishes current availability, leaves the old write's outcome unknown, and retains the stopped or failed continuation. Ordinary same-connection movement, spawns, heals or stale socket packets cannot release it. Low or unavailable HP during return stops the trip and keeps its original deadline; recovery does not silently start another return attempt.

## Source and proof

Source pin: public protocol commit `4099e2c`. `PacketRespawn.cs` ignores disconnected, alive or input-cooldown requests and ordinarily revives at 1 HP before returning to the save point. `Map.TeleportEntity` emits clear then Warp; `PacketPlayerReady` activates EnterServer. `CommandBuilder.SerializeEntityDataV2` supplies the nearby-player SP placeholders.

Deterministic controller tests cover a complete raw-packet Sit/Stand and real portal/walk return, initial-dead Start, destination B during interrupted entry travel, source-shaped readiness failures, Stop at each phase, no-ACK/send-throw uncertainty, subsequent death budgets, known/unknown SP, recovery/return deadlines, old socket frames, final-allowance reload, missed telemetry, successor ownership, stale completion and the 64-guard bound. Native UI and deployed automatic respawn remain unrun in this implementation lane. No live death or resource-changing action was induced.
